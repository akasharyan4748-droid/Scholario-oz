SCHOLARIO / SCHOLARIO-OS
SUBJECT ECOSYSTEM ARCHITECTURE — STUDENTS & CLASSES + EXAMINATIONS
FULL CROSS-MODULE IMPLEMENTATION

IMPORTANT:
DO NOT RUSH THIS IMPLEMENTATION.

This is NOT a small UI change.

We are now fixing the underlying SUBJECT architecture of the school ERP.

Students & Classes and Examinations must be treated as TWO CONNECTED MODULES of the SAME academic data system.

The goal is to establish one clean, reliable, normalized Subject ecosystem that can later be consumed consistently by:

Students & Classes
Examinations
Timetable
Marks Entry
Results
Report Cards
Reports / Analytics
Teacher workflows
Student workflows
and any future academic module.

Take your time.

First inspect the existing project architecture, database/schema, services, APIs, seed data, class model, section model, stream model, subject model, examination model, result/marks model and all existing subject-related logic.

Do NOT blindly create a second parallel subject system.

Do NOT hardcode the same subjects independently in multiple modules.

Do NOT solve this with visual filtering only.

Implement the correct underlying architecture so the entire ecosystem remains synchronized.

============================================================
PART 1 — CORE PRODUCT DECISION
============================================================

We are establishing this rule:

STUDENTS & CLASSES is the primary source of truth for which subjects exist for each class/stream.

EXAMINATIONS must consume those configured subjects.

RESULTS / REPORTS / MARKS must consume the same canonical subject identity.

The same subject must NOT become different subjects simply because it appears in different modules.

For example:

Hindi in Class 6,
Hindi in Class 7,
Hindi in Class 9,
Hindi in Class 10

must still resolve to the same canonical subject identity where appropriate, while maintaining its class applicability.

Likewise:

Physics for Class 11 Science PCM
Physics for Class 11 Science PCB
Physics for Class 12 Science PCM
Physics for Class 12 Science PCB

must resolve through the same canonical subject concept, with class/stream applicability determining where it is available.

The UI may display subjects in class-specific contexts, but the underlying identity must remain normalized.

PART 10 — SUBJECT REMOVAL
============================================================

Separate:

SUBJECT MASTER

from:

CLASS SUBJECT ASSIGNMENT

Example:

Computer Science

can exist in the subject master.

can be assigned or unassigned.
