26. CAPTAIN VS VICE CAPTAIN
============================================================

Do not assume they need identical permissions.

Create a permission matrix.

Example starting model:

CLASS CAPTAIN:

Can:

• access class leadership dashboard
• view class announcements relevant to their section
• see permitted class tasks
• create/request class reminders
• submit class-wide requests to teacher
• report class issues to teacher
• help coordinate permitted class activities
• see class event/task status where authorized
• assist teacher with non-sensitive coordination
• access leadership notices
• view permitted class-level participation summaries

Cannot:

• edit attendance
• mark another student's attendance
• edit marks/results
• change grades
• view private academic records
• view fee details
• view health/medical information
• view parent contact information
• access disciplinary records
• change student profiles
• remove students
• change class assignments
• appoint another leader
• access administrative settings
• send school-wide official notices
• access teacher-only data

77. FINAL PRODUCT PHILOSOPHY
============================================================

SCHOLARIO STUDENT WORKSPACE

should NOT feel like:

"an ERP with many menus."

It should feel like:

"my personal school workspace."

The system should intelligently reveal functionality
based on who the student is and what is actually relevant
to that student.

NORMAL STUDENT
→ sees normal student capabilities.

TRANSPORT STUDENT
→ automatically gets Transport.

CLASS CAPTAIN
→ automatically gets Leadership capabilities.

VICE CAPTAIN
→ automatically gets the narrower permitted capabilities.

STUDY MATERIALS
→ shows only resources relevant to that student.

Everything else remains invisible.

The interface should stay simple
BECAUSE the backend is intelligent.

That is the goal.
