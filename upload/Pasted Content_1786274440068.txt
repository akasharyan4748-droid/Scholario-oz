SCHOLARIO — PRINCIPAL PORTAL
STUDENTS & CLASSES MODULE
CLASS DETAILS UX/UI + DATA BEHAVIOR + DESIGN SYSTEM REFINEMENT

ROLE / CONTEXT

We are working specifically on the PRINCIPAL role's:

Students & Classes

module inside SCHOLARIO — Enterprise School ERP.

This is an existing, actively developed product.

DO NOT redesign the entire product.

DO NOT invent a new visual identity.

DO NOT treat this as a generic school ERP UI exercise.

The objective is to evolve the existing SCHOLARIO Students & Classes experience into a polished, premium, production-grade enterprise experience while staying completely consistent with the design language and interaction patterns already established elsewhere in the application.

The most important principle for this task:

UNDERSTAND THE EXISTING SCHOLARIO SYSTEM FIRST.
THEN IMPROVE IT.

Do not blindly implement every sentence below as an isolated UI instruction.

Use these requirements as product intent and constraints, then use your engineering/design judgment to arrive at the cleanest implementation.

============================================================
13. SUBJECT MANAGEMENT
============================================================

Subjects are manageable from the Subjects tab.

The user should be able to:

- view active subjects
- add subject where permitted
- edit/manage subjects
- archive subjects

Archive must actually work.

Do not implement archive as merely hiding the card from the screen.

It must update the underlying state/data.

When a subject is archived:

- it leaves the active subject list
- it should no longer be treated as an active subject for new assignment purposes
- it becomes available through the appropriate archive view
- it can be restored
- permanent deletion, if supported by the application, remains distinct from archive

Archive and Delete must never be treated as the same operation.

Use the same interaction pattern elsewhere in SCHOLARIO where possible.

============================================================
25. REMOVE VS REPLACE
============================================================

This distinction is critical.

If:

Sunita Rao

is replaced by:

Rohan Mehta

that is a REPLACEMENT.

Sunita Rao is still an active teacher.

Do not archive Sunita Rao.

Do not delete Sunita Rao.

Only the class relationship changes.

If the user explicitly chooses:

Remove

then the class/section assignment becomes vacant.

The teacher remains active globally.

Removing a teacher from a class is NOT archiving the teacher.

============================================================
26. INLINE CROSS MUST NOT BYPASS SAFETY
============================================================

If an existing selected-teacher control contains an ×:

do not allow it to silently mutate the assignment.

A destructive action should not be hidden behind an innocent-looking tiny tap target.

Prefer removing the inline destructive × if it does not add meaningful value.

If the × remains, it must follow the same confirmation/pending-change behavior as the explicit Remove action.

Never:

tap ×
→ assignment instantly disappears
→ no confirmation
→ no way to understand what happened.

The UX must be safe.

============================================================
28. ARCHIVE IS NOT REMOVE
============================================================

This distinction must exist throughout SCHOLARIO.

REMOVE ASSIGNMENT:

Teacher remains active.

ARCHIVE TEACHER:

Teacher record becomes archived/inactive.

DELETE TEACHER:

Teacher record is permanently removed.

These are three different operations.

Do not mix their state transitions.

============================================================
29. TEACHER ARCHIVE LIFECYCLE
============================================================

Teacher records should have a proper lifecycle.

Conceptually:

ACTIVE
↓
ARCHIVED
↓
DELETED

Active teachers:

- appear in active Teachers list
- appear in active assignment selectors
- can be assigned where permitted

Archived teachers:

- disappear from normal active assignment selectors
- remain in Archive
- preserve their record/history as supported
- can be restored

Deleted teachers:

- are permanently removed
- cannot be restored through Archive
- would need to be created again if required

Use the existing SCHOLARIO data architecture rather than inventing an unnecessary parallel lifecycle system.

============================================================
30. IMPORTANT — ARCHIVING AN ASSIGNED TEACHER
============================================================

Think carefully about this edge case.

Suppose:

Class Teacher → Sunita Rao

Then Sunita Rao is archived.

The system must not leave the application in an inconsistent state where an inactive teacher is freely selectable as an active teacher.

After archival:

- Sunita Rao must not appear in active teacher selectors
- the class should clearly reflect that the current assignment references an archived teacher if historical/current relationship requires it
- the Principal should be able to replace the assignment with an active teacher
- the archived record must remain recoverable through Archive

Do not silently destroy historical data.

Do not silently create duplicate teacher records.

Use stable teacher IDs.

============================================================
31. RESTORE
============================================================

Restoring an archived teacher should restore the teacher's active status.

They should then become available again in:

- active Teachers
- teacher selectors
- permitted assignment workflows

Do not create a new teacher identity on restore.

The original teacher ID remains the identity.

Use strong confirmation.

Do not use Delete as a casual UI action in the main Teachers/Class Details screens.

36. INPUT/CURSOR BUG
============================================================

→ clicks somewhere else
→ comes back to the field
→ the text/caret position behaves incorrectly
→ typing can begin from the wrong position.

Do not solve this with a cosmetic CSS workaround.
