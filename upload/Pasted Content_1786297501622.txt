SCHOLARIO — TIMETABLE FINAL UX / WORKFLOW REFINEMENT
PRINCIPAL ROLE
MASTER TIMETABLE → EDIT → SAVE → PUBLISH → NOTIFY → CHANGE INDICATORS

IMPORTANT:

The current Timetable implementation is already visually strong.

DO NOT rebuild the module from scratch.

DO NOT replace the current timetable layout.

DO NOT introduce a completely different dashboard.

The current design, spacing, cards, timetable grid, filters, day selector, empty slots, breaks, summary cards and overall Scholario visual language are already good.

This pass is about making the TIMETABLE WORKFLOW smarter, cleaner, safer and more production-grade.

The goal is:

VIEW
→ EDIT
→ SAVE
→ REVIEW
→ PUBLISH
→ NOTIFY
→ TEMPORARY CHANGE INDICATORS

The Principal should feel that they are managing one authoritative SCHOOL MASTER TIMETABLE.

============================================================
2. PRODUCT PRINCIPLE
============================================================

The Timetable should behave like a:

MASTER SCHEDULE WORKSPACE

not just a timetable viewer.

There is ONE authoritative timetable.

Principal edits that timetable.

From that same timetable:

- students get their class/section timetable
- teachers get their personal timetable
- Principal gets the complete school-wide timetable

Do NOT create separate timetable datasets for each role.

The same master timetable must remain the source of truth.

============================================================
10. SAVE ≠ PUBLISH
============================================================

THIS IS CRITICAL.

There are two different actions:

SAVE
and
PUBLISH

They must NOT be treated as the same thing.

SAVE means:

"The Principal has updated the master timetable."

PUBLISH means:

"The updated timetable is now officially released to users."

Therefore:

Edit
→ change timetable
→ Save Changes

After saving:

the timetable is updated in the master schedule.

BUT the publish action should now appear.

============================================================
11. PUBLISH ACTION ONLY AFTER A CHANGE IS SAVED
============================================================

Do NOT permanently show a large Publish button.

Normal state:

[ Export ]

No Publish action.

After Principal saves timetable changes:

a compact Publish action appears.

Example:

[ Export ] [ Publish Update ]

or:

[ Export ] [ ↑ Publish ]

Use an appropriate icon.

The exact label can be shorter if the icon and context are clear.

This should visually communicate:

"There is a saved timetable change waiting to be published."

A tiny animated indicator can subtly draw attention to it.

Do NOT use an aggressive notification dot.

============================================================
12. WHY PUBLISH IS IMPORTANT
============================================================

The Principal may make several changes before officially notifying users.

Example:

Change 1:
Class 2-A Mathematics moves from Period 1 → Period 2.

Change 2:
Teacher changes from Rohan → Sunita.

Change 3:
Room changes from Room 102 → Room 104.

The Principal can save these changes.

Then review the timetable.

Only when satisfied:

Publish.

This is much safer than notifying students after every individual edit.

============================================================
13. PUBLISH CONFIRMATION
============================================================

Clicking Publish should NOT immediately send notifications.

Open a compact, premium confirmation surface.

Example:

Publish timetable update?

3 changes will be shared with affected students and teachers.

[Cancel]       [Publish Update]

Keep it short.

No giant confirmation modal.

Use the same polished confirmation language established elsewhere in Scholario.

============================================================
14. SHOW WHAT WILL BE PUBLISHED
============================================================

The Publish confirmation should give the Principal enough information to understand the changes.

Do NOT show a giant diff.

Show a compact summary.

Example:

3 timetable changes

• Class 2-A · Period 1
  Mathematics moved to Period 2

• Class 9-A
  Teacher changed

• Class 10-A
  Room changed

Use concise text.

Icons are encouraged.

The Principal should understand the changes in 2–3 seconds.

============================================================
15. AFTER PUBLISH
============================================================

After successful publishing:

1. The publish action disappears.

2. The timetable becomes the current published timetable.

3. Notification events are created.

4. A premium success animation appears.

Example:

✓ Timetable published

Keep it small.

Do not use a giant celebratory animation.

Something subtle like:

checkmark
soft pulse
tiny sparkle
fade

is enough.

============================================================
16. NOTIFICATION SYSTEM
============================================================

This is important.

When a timetable update is published, users should receive a notification.

But do NOT send a generic:

"Timetable updated."

The notification should communicate what actually changed.

Example:

📅 Timetable updated

Class 2-A
Mathematics moved to Period 2.

or:

📅 Timetable update

Room 102 → Room 104
Period 3 · Science

Keep text extremely short.

The notification should look premium.

Use:

small timetable/calendar icon
short title
one-line change summary
subtle animation

============================================================
17. WHO GETS NOTIFIED
============================================================

The notification system should be intelligent.

Do NOT blindly notify every user for every tiny change if the architecture allows recipient scoping.

The default should be:

AFFECTED USERS.

For example:

If Class 2-A Period 2 changes:

notify:

- students of Class 2-A / relevant section
- teacher assigned to that period
- teacher affected by the change

If a school-wide schedule change genuinely affects everyone:

notify all relevant students and teachers.

Principal should not create notification spam.

If the current notification architecture supports recipient targeting, use it.

If it does not, prepare the data model cleanly rather than faking it.

============================================================

============================================================
19. CHANGE HISTORY / VERSIONING
============================================================

Because this is a master timetable, changes should be trackable.

Each publish should conceptually create a new timetable version.

Example:

Do not necessarily expose all of this prominently in the UI.

But the architecture should be capable of knowing:

when it changed
who published it

This will make future audit/history features possible.

============================================================
20. THE 3-DAY "UPDATED" INDICATOR
============================================================

This is one of the most important visual requirements.

After a timetable change is published:

the affected timetable entries should display a tiny temporary indicator.

It must feel:

premium
cute
subtle
unique
clean
not childish

Do NOT use a large red badge.

Do NOT write:

UPDATED UPDATED UPDATED

everywhere.

Instead create a tiny visual marker.

Possible concept:

near the slot corner

with a small label:

New

or:

Updated

The marker should be visually lightweight.

============================================================
21. EXACT 72-HOUR LIFETIME
============================================================

The change indicator should remain visible for:

72 hours / 3 days

from the actual publication timestamp.

Do NOT use:

"hide after three page loads"

Do NOT use:

"hide after session"

Do NOT hardcode a calendar date.

Use:

publishedAt + 72 hours

Then automatically stop showing the indicator.

============================================================
22. CHANGE INDICATOR CONTENT
============================================================

The tiny indicator can be:

✨ New

or:

↻ Updated

or another subtle Scholario-native visual.

The exact visual is up to you.

But it should be tiny enough that it does not destroy timetable readability.

Hover/tap can reveal:

Updated today
Period changed

or:

Updated 2h ago

The detailed change should NOT require the user to open a huge modal.

============================================================
23. CHANGE INDICATOR ANIMATION
============================================================

Use a very subtle animation.

Do not make the timetable look like a Christmas tree.

============================================================
24. CHANGE INDICATOR MUST BE DATA-DRIVEN
============================================================

Do NOT simply add a CSS badge to every timetable entry.

Only affected entries should receive the indicator.

For example:

Mathematics
UPDATED

Monday Period 2

Only the actual changed entries should show it.

============================================================

ONE SOURCE OF TRUTH.

============================================================
31. EDIT MODE + PENDING PUBLISH
============================================================

Important edge case:

Principal saves changes.

Publish is now pending.

Then Principal enters Edit again and makes another change.

The system must handle this cleanly.

Do NOT silently overwrite the previous saved-but-unpublished changes.

Prefer:

Draft / unpublished changes are accumulated into the pending publish version.

When Principal saves again:

the pending publish summary updates.

Example:

Previously:

2 changes ready to publish.

Principal makes another change.

Now:

3 changes ready to publish.

Then Publish publishes the current accumulated change set.

============================================================
32. CANCEL BEHAVIOR
============================================================

If Principal enters Edit mode and changes something but clicks Cancel:

discard only UNSAVED changes.

Do NOT discard already-saved pending publish changes.

Example:

Saved:
2 changes ready to publish.

Enter Edit.

Make another change.

Cancel.

The 2 saved changes remain pending publication.

This distinction is extremely important.

============================================================
33. CONFLICTS + PUBLISH
============================================================

Principal must never be able to publish an invalid timetable.

If a conflict exists:

Publish should be disabled.

Example:

⚠ 1 conflict

Resolve conflict before publishing.

Do not allow publication of a known teacher/class/room collision.

============================================================
34. SAVE VS PUBLISH STATUS
============================================================

Think of timetable state as:

CURRENT PUBLISHED
+
PENDING SAVED CHANGES
+
UNSAVED EDITS

The UI should understand these three states.

UNSAVED EDITS:

PENDING SAVED CHANGES:

CURRENT PUBLISHED:

No publish action.

This should be reflected in the actual architecture, not only visually.
