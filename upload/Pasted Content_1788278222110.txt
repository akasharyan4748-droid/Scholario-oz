APPLICATIONS & FORMS — FINAL PRODUCTION IMPLEMENTATION
=======================================================

We need to properly finish and redesign the Applications & Forms system in SCHOLARIO-OS.

This is NOT just a UI polish task.

The current implementation has three major problems:

1. Form lifecycle is incomplete.
2. Draft forms cannot be properly deleted/published.
3. The actual application/consent document is still not implemented to the required professional A4 single-page standard.

You must inspect the existing implementation, routes, components, database/schema, form relationships, collections, responses, permissions and existing UI before making changes.

Do not create a disconnected mock implementation.
Do not hardcode a separate demo system.
Do not replace existing data with fake data.

Reuse and improve the existing architecture.

=======================================================
PART 1 — APPLICATIONS & FORMS IS A GENERIC SYSTEM
=======================================================

Applications & Forms is NOT an Educational Tours module.

Educational Tour is only ONE possible use case.

The system must support things such as:

- Educational Tour Consent
- Sports Participation Consent
- Competition Registration
- Workshop Registration
- Event Registration
- Parent Consent
- Student Declaration
- General Application
- Permission Form
- Other school-created forms

Therefore:

DO NOT use "Tours" terminology globally.

Do NOT use:

"New Educational Tour"

as the main creation action.

Use:

"+ New Form"

The page description should remain generic, for example:

"Create and manage school applications, registrations and consent forms"

The form title/type should determine what the individual form is about.

=======================================================
PART 2 — FORM LIFECYCLE
=======================================================

Every newly created form MUST start as:

DRAFT

Never publish automatically.

Correct lifecycle:

CREATE
↓
DRAFT
↓
EDIT
↓
PREVIEW
↓
PUBLISH
↓
OPEN / ACTIVE
↓
CLOSE
↓
ARCHIVE

A newly created form must never immediately become active.

=======================================================
PART 3 — DRAFT ACTIONS
=======================================================

For a DRAFT form, the Principal must have:

- Edit
- Preview
- Publish
- Duplicate as new draft
- Delete draft

The Principal must be able to delete a draft because mistakes happen.

Example:

Principal creates a form.

Realizes:

"Wrong fee"
"Wrong date"
"Wrong form"
"Created by mistake"

They should be able to simply delete the draft.

Do NOT force them to publish first.

Do NOT hide delete inside some unrelated settings screen.

=======================================================
PART 4 — DELETE DRAFT
=======================================================

When deleting a draft, use a proper confirmation dialog.

Title:

Delete draft?

Message:

"This form has not been published. Deleting it will permanently remove this draft."

Actions:

Cancel
Delete Draft

Actually delete the draft from the backend/database.

Do not merely hide it from the UI.

Do not use browser alert() unless the existing application architecture absolutely requires it.

=======================================================
PART 5 — PUBLISHED FORMS
=======================================================

Once published, destructive deletion must NOT be available.

Published forms can contain:

- responses
- consent records
- signatures
- payment relationships
- student information
- historical records

Therefore:

PUBLISHED / OPEN:
- View
- Preview
- Edit where safe
- Close
- Duplicate as new draft

CLOSED:
- View
- Preview
- Duplicate as new draft
- Archive

ARCHIVED:
- View
- Duplicate as new draft

Do NOT expose Delete for published/closed/archived forms.

=======================================================
PART 6 — PUBLISH
=======================================================

A Draft must have a clear Publish action.

The Principal should be able to:

Save Draft
Preview
Publish

Publishing should actually persist the status.

On publish:

DRAFT → OPEN/PUBLISHED

After publishing:

- form becomes available according to existing access/sharing rules
- responses can be submitted
- linked payment/collection functionality becomes active where applicable
- Delete disappears

Show a confirmation before publishing if appropriate:

"Publish form?"

"Once published, this form can be shared with students/parents and cannot be permanently deleted."

Buttons:

Cancel
Publish Form

=======================================================
PART 7 — SAFE EDITING
=======================================================

Draft forms:

Fully editable.

Published forms:

Allow safe edits.

If responses already exist, prevent structural edits that could invalidate historical responses.

For example:

A field that has already received responses should not be silently deleted or changed into a different field type.

If an edit is unsafe, clearly explain:

"This field cannot be changed because responses have already been received."

Never corrupt historical responses.

=======================================================
PART 8 — APPLICATIONS & FORMS LIST
=======================================================

The current table is directionally correct, but make it a proper generic form-management table.

Columns:

FORM
TYPE
IN-CHARGE
DEADLINE
RESPONSES
PAYMENT

ACTIONS

Example:

The first column should show the actual form title.

Do not make everything appear as a tour.

=======================================================
PART 9 — ACTION MENU MUST BE STATE-AWARE
=======================================================

CURRENT PROBLEM:

The Actions menu currently only has:

View details
Duplicate as new draft

That is insufficient.

Implement:

DRAFT:
- Edit
- Preview
- Publish
- Duplicate as new draft
- Delete draft

OPEN / PUBLISHED:
- View details
- Preview
- Edit
- Close
- Duplicate as new draft

CLOSED:
- View details
- Preview
- Duplicate as new draft
- Archive

ARCHIVED:
- View details
- Duplicate as new draft

Do not show invalid actions.

=======================================================
PART 10 — FORM CREATION
=======================================================

"+ New Form" should open a proper creation flow.

Every new form begins as DRAFT.

Principal can configure:

- Form title
- Form type
- Description
- Deadline
- Session
- Target students/classes
- Fields
- Required/optional fields
- Consent requirement
- Signature requirement
- Payment requirement
- Optional linked collection
- Submission rules

At the end:

Save Draft
Preview
Publish

Do NOT auto-publish.

=======================================================
PART 11 — ACTUAL FORM EXPERIENCE
=======================================================

The existing application/consent form implementation is NOT acceptable.

There is currently a web-style/multi-page form experience that does not match the required final product.

Replace/improve it.

There should be two distinct experiences:

A. ONLINE FORM / SUBMISSION EXPERIENCE
B. OFFICIAL A4 DOCUMENT / PRINT PREVIEW

They are NOT the same thing.

-------------------------------------------------------
A. ONLINE FORM
-------------------------------------------------------

The online form should be simple and easy for a parent/student to complete.

Use only the fields required by that specific form.

Do not dump the entire student profile into every form.

If student information already exists in SCHOLARIO, prefill it where appropriate.

For example:

Student Name
Admission Number
Class
Section

can be automatically populated when known.

Do not ask the parent to manually type information the school already has unless there is a genuine reason.

-------------------------------------------------------
B. OFFICIAL A4 DOCUMENT
-------------------------------------------------------

This is the most important part.

The submitted form must be representable as an official school document.

The document MUST be:

- A4 portrait
- single page for normal forms
- print-ready
- PDF-ready
- professionally typeset
- clean
- formal
- restrained
- readable
- suitable for school records

It should look like a professionally prepared Microsoft Word school proforma.

It should NOT look like a SaaS dashboard.
